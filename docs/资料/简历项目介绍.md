## 一、简历写法（可直接使用）

### 项目经历：言权 · AI 消费者维权助手（独立开发）

**角色**：独立开发者 · 全栈
**时间**：2026.6 – 2026.8

**项目简介**：一款基于 AI 大模型的消费者维权微信小程序。用户口述/输入维权经历，系统自动生成专业投诉信、匹配法律依据、推荐维权路径与沟通话术。定位为黑猫投诉、12315 等投诉渠道的"前置智能助手"，已形成完整可交付产品（后端 + 小程序 + 测试 + 部署方案）。

**技术栈**：TypeScript / React / Taro 4 / SCSS ｜ Python / FastAPI / SQLite ｜ 阿里云百炼（通义千问）/ DashScope ASR ｜ Docker

**核心工作与成果**：

1. **设计并实现 6 步 AI 生成管线**：事实提取 → 法律检索（本地知识库 20+ 条文语义匹配，预留北大法宝接口）→ 投诉信生成 → 商家资质建议 → LLM 自我审查修复 → 沟通话术生成，输出结构化 JSON。
2. **独创"演示模式"工程方案**：无 API Key 时自动降级为纯规则生成管线（正则事实提取 + 标签法律匹配 + 模板信函），接口结构与 LLM 模式完全一致，实现**零配置开箱可演示、可测试**——面试现场无需联网配 Key 即可跑通全流程。
3. **从 0 到 1 构建完整产品**：FastAPI 后端（认证/投诉/OCR 三模块、token 鉴权、用户数据隔离、状态机）；Taro 4 微信小程序全新 UI（深海蓝+鎏金设计系统，7 个页面，语音/文字/截图三种输入）；30 个 pytest 自动化测试全通过；Docker 一键部署 + 微信上线手册。
4. **产品化能力**：完成竞品分析（黑猫/12315 差异化定位）、PRD、用户协议/隐私政策/免责声明，形成可交付、可上线、可复用的完整项目。

**可量化**：后端 30 个自动化测试全部通过；小程序双端编译通过；覆盖 8 大投诉场景、20+ 法律条文、7 类商家资质查验。

>
> 技术上我独立完成了全栈：FastAPI 后端做了一个 6 步 AI 生成管线，通义千问做语义理解和生成，本地法律知识库做条文匹配，还有 LLM 自我审查保证质量；小程序端用 Taro 4 写了 7 个页面和完整设计系统。比较特别的一个工程点是：我设计了演示模式，没有 API Key 时系统自动降级成纯规则管线，接口结构完全一致，所以这个项目在任何环境开箱就能跑、能测、能演示。"

## 三、面试高频问题准备

### Q1：这个项目最难的环节是什么？

> 法律条文匹配的准确性。解决方案是"知识库 + 语义匹配 + 自我审查"三层：
> 1. 先建 20+ 条高频消费纠纷条文的知识库，按场景打标签；
> 2. LLM 基于用户事实做语义匹配，而不是死板的字符串匹配；
> 3. 生成后再让 LLM 做一轮质检，检查金额、法条、诉求是否完整，不合格自动修复。
> 三层叠加把生成质量从"能用"提升到"接近律师起草"。

### Q2：为什么设计演示模式？

> 两个原因：第一，项目要交付、要面试演示，不能依赖外部 API Key，否则现场跑不起来；第二，从工程上讲，AI 能力是可降级的，把"外部依赖"和"核心逻辑"解耦是生产级系统的通用思路。实现上我把生成管线抽象成两个实现：LLM 版和规则版，通过配置自动切换，接口契约完全一致，测试也能在 CI 里稳定运行。

### Q3：怎么保证用户数据安全？

> 三层：一是传输和鉴权，小程序带 token 访问，后端每个接口做归属校验，A 用户拿不到 B 用户的记录；二是存储，SQLite 落盘 + 上传文件用完即删；三是合规，内置隐私政策、用户协议和免责声明，符合《个人信息保护法》要求。

### Q4：为什么用 SQLite 不用 MySQL？

> MVP 阶段 SQLite 零配置、单文件、够用且可靠，测试也用临时库保证隔离；但我在数据库层做了抽象，后续用户量上来可以平滑迁移 PostgreSQL，部署文档里也写了迁移路径。

### Q5：AI 生成内容有法律风险怎么办？

> 产品层面做了三道防线：结果页和详情页都带免责声明，标注"不构成法律意见"；用户协议明确责任边界；生成内容允许用户编辑修改后再使用。这其实是"AI 应用合规"的通用实践。

### Q6：和黑猫投诉、12315 的关系？

> 不是竞争，是上下游。它们做"渠道"，我做"内容生产"。用户流程是：在言权生成投诉信 → 复制到 12315 提交（求权威）或黑猫曝光（求速度）。这也是我从竞品分析里得出的差异化定位，避开了和大平台正面竞争，反而可以谈生态合作。
