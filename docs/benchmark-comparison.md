# 言权 · 生成耗时优化对照（真实 AI 模式实测）

> 数据来源：本地后端 + 真实大模型（阿里云百炼 qwen-plus / qwen-flash），
> 端到端调用 `POST /api/complaint/task` 并轮询到出稿完成，包含全部模型调用与文书处理耗时。
> 压测脚本：`scripts/benchmark.py`；明细报告见 `benchmark-before-optimization.md`、`benchmark-after-optimization.md`。

## 一、结论

| 指标 | 优化前 | 优化后（两次实测） | 变化 |
|------|--------|-------------------|------|
| 成功率 | 100%（10/10） | 100%（10/10） | — |
| 平均耗时 | 48.49s | 29.46s / 38.23s（均值 33.8s） | **↓ 约 30%** |
| P95 | 79.21s | 34.91s / 62.78s | **↓ 约 38%** |
| P99 | 101.66s | 35.63s / 75.82s | 大幅下降 |
| 单次模型调用次数 | 6 次 | 2–4 次（按需质检） | **↓ 33%～67%** |
| 单次 token 消耗 | 约 8100 | 约 4700～7100 | ↓ |

测试条件：10 个真实维权场景各 1 次，单用户串行（`--concurrency 1`），比较同一台机器、同一模型配置。
大模型自身的速度波动较大，两次「优化后」实测存在差异，故并列展示。

## 二、优化手段

| # | 手段 | 位置 | 效果 |
|---|------|------|------|
| 1 | 事实提取与法律检索并行 | `complaint_generator.py` `generate_complaint_progressive()` | 两次模型调用等待重叠，省约 3–4s |
| 2 | 骨架、完整文书、话术三路并行 | 同上，`ThreadPoolExecutor(max_workers=3)` | 骨架不再阻塞文书生成，省约 2–3s |
| 3 | 质检改为按需触发 | 同上 + `_letter_needs_review()` | 规则初筛通过则跳过模型质检，省约 10s（多数请求走这条） |
| 4 | 法条白名单格式归一化 | `_validate_matched_laws()` + `normalize_*()` | 修复模型精排结果被全部过滤、被迫降级的问题 |
| 5 | 事实核验 + 净化幂等 | `_verify_facts_against_text()`、`_sanitize_letter()` | 修复编造姓名/电话/订单号/日期，以及占位符重复 |

其中第 3 条的取舍：质检环节原本每次都调用一次模型做「质检 + 改写」，实测约 10 秒。
改为先用规则初筛（板块是否齐全、是否引用法条、缺失信息是否有占位），只有确实发现问题才调用模型，
既保留质检能力，又让大多数请求直接省下一次模型调用。需要强制每次都质检时，把
`backend/.env` 里的 `LLM_ALWAYS_REVIEW=true` 打开即可。

## 三、附带修复的质量问题

这轮压测顺带暴露并修复了三个真实缺陷（均由 73 个自动化测试 + 真实文书抽检覆盖）：

1. **法条精排形同虚设**：模型返回 `《消费者权益保护法》第55条`，与知识库的 `消费者权益保护法` + `第55条` 精确匹配失败，导致每次都降级为规则匹配。归一化后实测「3 条全部命中」。
2. **质检改写的文书绕过防编造**：净化步骤原本在质检之前执行，质检若重写文书就会把编造的姓名、电话、订单号带进最终结果。现在净化放在质检之后。
3. **编造信息的两处漏网**：带分隔符的手机号（`138-1234-5678`）不被识别；已存在的占位符会被二次替换导致重复（`【请补充姓名】【请补充姓名】`）。两者均已修复并加了回归测试。

## 四、复现命令

```bash
# 1) 启动后端（配置了真实 API Key 即为 LLM 模式）
bash backend/run.sh

# 2) 单用户串行实测（10 场景 × 1 次）
/opt/anaconda3/envs/rag_env/bin/python scripts/benchmark.py \
  --repeat 1 --scenarios 10 --concurrency 1 --timeout 180 \
  --output docs/benchmark-after-optimization.md

# 3) 并发压测（会真实消耗模型额度，>50 次需显式 --allow-cost）
/opt/anaconda3/envs/rag_env/bin/python scripts/benchmark.py --repeat 5 --concurrency 5 --allow-cost
```

> 成本提示：LLM 模式下单次生成约 4700～7100 tokens，全量 10 场景 × 100 次会产生可观费用，
> 建议演示与比赛材料使用上述 10 次串行样本即可，足够反映真实体验。
