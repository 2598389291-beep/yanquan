> 用法：每节先看「一句话」，再背「口述版」（照着念就能讲清），最后对照「代码位置」核一遍。

## 1. 一句话简介

**给谁用**：遇到消费纠纷、想维权但不知道怎么写材料、该找哪个部门、证据怎么留的普通消费者。

**解决什么问题**：把「不敢开始、不会写、不知道流程」变成「照着做就行」。用户只要口述一段经历，就能拿到一份规范可提交的投诉文书、匹配到的法律条文、该留哪些证据的清单、以及第一条该走哪条渠道。

**怎么实现**：微信小程序（Taro 4 + React + TypeScript）作为前端，后端是 FastAPI + SQLite，跑在同一条「六步 AI 生成管线」上：事实提取 → 法律检索 → 投诉信生成 → 资质建议 → 质检修复 → 话术生成。法律侧用本地 108 条法律知识库做 RAG 召回，再由大模型在候选里精排，最后用白名单校验兜底，防止编造法条。

**口述版（约 30 秒）**：
> 言权是一个消费者维权小程序，给普通人用的。用户把维权经历说出来或者打出来，后端一条六步的 AI 管线会依次做：提取事实、匹配法律、生成投诉信、给商家资质建议、自我质检修复、再给一套沟通话术。法律部分不是让大模型随便编，而是先从本地 108 条知识库里检索候选，再让模型在候选里选，选完还要过一遍白名单校验，不在知识库里的法条一律丢掉。没配 API Key 的时候会自动切到纯规则管线，功能结构完全一样，所以演示和测试永远跑得通。

**代码位置**：`backend/main.py`（应用入口、路由挂载）、`backend/services/complaint_generator.py`（管线主体）、`backend/services/demo.py`（规则管线）、`backend/services/law_seed.py`（108 条法律知识库种子数据）。

## 2. 主链路：六步 AI 管线

### 逻辑上的六步（对外讲解用这个顺序）

| 步骤 | 名称 | 说明 | 进度 |
|------|------|------|------|
| Step 1 | 事实提取 | 把用户口语转成结构化字段：平台/商品/金额/时间/商家/问题类型/诉求/缺失字段/类别 | 15% |
| Step 2 | 法律检索 | 先用 RAG 召回候选条文，再让模型精排 1–3 条，最后过白名单校验 | 30% |
| Step 3 | 投诉信生成 | 先出骨架（10 秒内可见），再补全完整文书 + 维权路径 | 42% / 55% / 62% |
| Step 4 | 商家资质建议 | 纯规则：按行业给出该查哪些资质、去哪查（如食品经营许可证、3C 认证） | — |
| Step 5 | 质检与修复 | 模型自查：金额、法条、诉求、时间、格式是否齐全，不合格就返回修订版 | 80% |
| Step 6 | 沟通话术生成 | 生成与商家 / 平台 / 12315 分阶段沟通话术 | 与 Step 3 并行 |
| — | 完成 | 落库、计数、返回完整结果 | 100% |

### 实际执行顺序（以代码为准，面试时主动说出来是加分项）

```
Step 1 事实提取        →  0.15
Step 2 法律检索        →  0.30
Step 3b 骨架           →  0.42 / 0.55（先把骨架推给前端）
Step 3 + Step 6 并行   →  0.62（ThreadPoolExecutor 并发跑「完整文书」和「话术」）
代码级兜底            →  _sanitize_letter() + _ensure_law_cited()
Step 4 资质建议        →  纯规则，插在并行块之后
Step 5 自我审查        →  0.80
收尾                  →  类别 + 渠道建议 + 法律溯源链接 → 1.0
```

三个要点，能被追问时展开：

1. **Step 3 和 Step 6 并行**：两者都只依赖「事实 + 法条」，互不依赖，所以用 `ThreadPoolExecutor(max_workers=2)` 同时跑，把两次模型调用的耗时压成一次。
2. **先给骨架再补全**：`_generate_skeleton()` 用快模型生成 250–450 字骨架，前端先看到内容，避免 50 秒白屏。
3. **每一步都可降级**：任意一步抛异常都会被 catch 住，回退到 `demo.py` 里同名的规则实现，最终保证返回结构完整。

**代码位置**：`backend/services/complaint_generator.py` → `generate_complaint_progressive()`（分阶段版，小程序走这条）、`generate_complaint()`（同步版，供 `POST /api/complaint/text` 使用）。

**接口链路**：`POST /api/complaint/task`（创建任务，立刻返回 `task_id`）→ 后台线程执行管线 → 前端轮询 `GET /api/complaint/task/{task_id}` 拿 `stage / progress / skeleton / result`。

## 4. 关键设计逐条讲

### 4.1 演示模式降级

**口述版**：
> 判断逻辑在 `config.py` 的 `demo_mode` 属性：只要 API Key 为空或是 `sk-xxx` 这类占位符，就返回 True，也就是演示模式。这时管线不会调用任何外部服务，直接走 `demo.py` 的纯规则实现：`extract_facts()` 用关键词和正则提取事实，`match_laws()` 按标签匹配法条，`generate_letter()` 套模板出信。关键是**两条管线返回的结构完全一致**——都是 `complaint_letter / legal_basis / action_path / category / legal_details / channel_advice / negotiation_script` 这些字段，所以前端和测试不用关心当前跑的是哪条。LLM 模式下还有第二层降级：每一步独立 try，失败就回退到 `demo.py` 里对应的同名函数，比如 `_extract_facts()` 挂了就调 `demo.extract_facts()`。这样任何一步失败都不会让整体崩掉。

**代码位置**：
- `backend/config.py:68` `demo_mode` 属性
- `backend/services/complaint_generator.py:487` 和 `:583` 两处演示模式分流
- 每一步降级：`complaint_generator.py` 里 `Step 1 / Step 2 / Step 3 / Step 6` 的 `except` 分支
- 规则实现：`backend/services/demo.py`（`extract_facts:67` / `match_laws:164` / `generate_letter:211` / `generate_negotiation_script:303` / `generate_complaint_demo:343`）
- 说明：`complaint_generator.py:472` 还留了一个整链兜底 `_rule_fallback()`，属于预留能力，当前未被调用

**可能被追问**：演示模式的信质量会不会很差？——会弱一些，但结构、法条来源、渠道建议都是真的，所以"能演示、能测试、能答辩"，这也是我在比赛和面试现场不用联网配 Key 就能跑通全流程的原因。

### 4.2 鉴权

**口述版**：
> 有三条登录路径，都收敛到 `database.py` 的 `create_or_update_user()`：邮箱密码、手机验证码、微信 `code2session`。密码用 PBKDF2-HMAC-SHA256 加随机盐、迭代 10 万次存哈希，校验用 `secrets.compare_digest` 防时序攻击，代码在 `auth.py` 的 `_hash_password()` 和 `_verify_password()`。登录成功后生成一个随机 token，有效期 30 天，存在用户表里；每次请求带 `Authorization: Bearer <token>`，后端用 `get_user_by_token()` 查，SQL 里直接带 `token_expires_at > datetime('now')` 这个条件，过期自然查不到。
> 另外我做了一个**游客也能用**的设计：如果没带 token，就走请求体里的 `user_id`（小程序端按设备生成的匿名 ID），只是这类用户受免费额度限制。路由层的 `_resolve_identity()` 统一处理这两种情况，返回 `(uid, 是否已认证)`。

**代码位置**：
- `backend/routers/auth.py:185` `email_login()`、`:206` `wechat_login()`、`:85` `_wechat_code2session()`（25 秒超时 + 2 次重试，容器出网走代理链路时跳过自签证书校验）
- `backend/routers/auth.py:68` `_hash_password()`、`:74` `_verify_password()`
- `backend/database.py:321` `create_or_update_user()`、`:387` `get_user_by_token()`、`:314` `TOKEN_TTL_DAYS = 30`
- `backend/routers/complaint.py:60` `_resolve_identity()`
- 额度：`backend/database.py:15` `FREE_GENERATION_LIMIT = 10`、`backend/routers/complaint.py:80` `_check_quota()`

**可能被追问**：为什么不用 JWT？——这个项目的鉴权需求很轻（单端、无跨服务），用「随机 token 落库」比 JWT 少一个密钥管理问题，而且**能即时失效**；缺点是每次请求多一次数据库查询，量大了就该上 Redis。

### 4.3 OCR（订单/聊天截图提取）

**口述版**：
> 用户上传订单截图后，走 `/api/ocr/extract` 或者证据上传接口。核心函数是 `ocr.py` 的 `_extract_order_info()`：把图片读成 base64，拼成 data URL，交给通义千问的视觉模型 `qwen-vl-max`，prompt 里明确要求返回严格 JSON，只提取六个字段——平台、订单号、下单时间、商品名称、金额、商家名称，找不到就填空字符串。
> 拿到结果后，`_extract_facts()` 会把这份订单信息合并进事实对象里，**只填空缺字段，不覆盖用户原话**。所以截图相当于帮用户补全了订单号和金额，用户不用重复输入。演示模式下 OCR 直接返回空结构，不调用外部服务。
> 语音那边同理：`asr.py` 的 `transcribe_audio()` 负责把录音转成文字，然后复用同一条文本管线，`_run_voice_task()` 就是"转写 + 调文本管线"。

**代码位置**：
- `backend/routers/ocr.py:26` `_extract_order_info()`（视觉模型 + JSON 解析）、`:79` `extract_order()`（接口）
- `backend/routers/complaint.py:90` `_try_extract_order_info()`（multipart 截图路径）
- `backend/routers/evidence.py:53` `upload_evidence_json()` / `:91` `upload_evidence()` / `:31` `_make_item()`

- 语音：`backend/services/asr.py:153` 起（演示模式判定 + 转写）

**可能被追问**：OCR 识别错了怎么办？——目前策略是"只在字段为空时填入"，用户可在提交前核对；后续可以在结果页加"修正订单信息"入口。

### 4.4 用户数据隔离

**口述版**：
> 隔离的原则是：**所有涉及具体记录的 SQL 都带 `user_id` 条件**，不存在"先查出来再判断是不是本人的"这种写法。比如列表查询 `get_complaints()` 的 where 子句第一项就是 `user_id = ?`；改状态 `update_complaint_status()` 会先 `SELECT ... WHERE id = ? AND user_id = ?`，查不到就返回 None，路由层转成 404；删除同理，`DELETE ... WHERE id = ? AND user_id = ?`，靠 rowcount 判断是否真的删掉了。
> 用户身份来自路由层的 `_resolve_identity()`：有 token 就用 token 对应的用户 ID，没有就用游客 ID。这样即使用户伪造了一个别人的 `complaint_id`，SQL 条件也查不到，越权直接变成"记录不存在"。
> 这三条路径都有测试覆盖：`test_text_generate_other_user_isolation`、`test_wrong_user_rejected`、`test_delete_ownership`。

**代码位置**：
- `backend/database.py:218` `get_complaints()`、`:237` `get_complaint_stats()`、`:256` `get_complaint_by_id()`、`:281` `update_complaint_status()`、`:301` `delete_complaint()`
- 路由侧：`backend/routers/complaint.py:60` `_resolve_identity()`、`:577` `complaint_detail()`、`:611` `update_status()`、`:652` `_remove()`
- 测试：`backend/tests/test_api.py:157`、`backend/tests/test_database.py:38`、`:43`

**可能被追问**：游客 ID 是客户端生成的，被别人猜到会怎样？——理论上可以冒充某个匿名 ID 读取该 ID 下的记录；这是"不登录也能用"换来的取舍。真要收紧，可以给游客 ID 也签发一个短期 token 存本地，或者要求写入操作必须登录。

### 4.5 状态机

**口述版**：
> 投诉记录有六个状态，定义在 `database.py` 的 `VALID_STATUSES`：`generated`（已生成）、`copied`（已复制）、`submitted`（已提交）、`following_up`（跟进中）、`resolved`（已解决）、`abandoned`（已放弃），中文标签在 `STATUS_LABELS` 里。
> 状态变更只有一条路：`update_complaint_status()`。它做三层校验——第一层是状态值必须在 `VALID_STATUSES` 里，不在就抛 `ValueError`；第二层是记录必须属于当前用户；第三层才是 UPDATE。接口层 `PATCH/POST /api/complaint/{id}/status` 把 `ValueError` 转成 400、把查不到转成 404。
> 前端后来弱化了"维权进度"这个模块，因为实际使用中用户把这里当工具用完就走，不会回来维护状态；但后端的状态机和统计接口都保留着，一是数据模型完整，二是后面做数据看板或者运营分析直接可用。

**代码位置**：
- `backend/database.py:267` `VALID_STATUSES`、`:271` `STATUS_LABELS`、`:281` `update_complaint_status()`
- 接口：`backend/routers/complaint.py:611` `update_status()`（同时支持 PATCH 和 POST）
- 统计：`backend/database.py:237` `get_complaint_stats()`

**可能被追问**：为什么不做状态流转合法性校验（比如"已解决"不能再变"已提交"）？——目前只校验取值合法性，没做有向图约束；如果要严格，可以加一张 `(from, to)` 白名单表。

## 5. 十个面试追问（自测用）

> 先自己口述回答，再对照括号里的要点。答不上来的，回上面第 3、4 节找代码。

1. **六步管线里，哪几步真的调了大模型？哪些是纯规则？**
   （事实提取、法律精排、骨架、完整文书、质检、话术调模型；资质建议、渠道建议、行动清单、证据清单、法律溯源链接都是纯规则。追问点：为什么要刻意保留规则部分——省钱、稳定、可解释。）

2. **大模型编法条怎么办？你的防幻觉是几层？**
   （三层：检索阶段只给候选 → 输出阶段白名单校验并用知识库原文覆盖内容 → 展示阶段每条法条带 `flk.npc.gov.cn` 官方检索链接。再加一层是代码级净化，编造的金额/日期/商家名会被替换成【请补充】。）

3. **第二步法律检索为什么要先 RAG 再让模型选，直接让模型答不行吗？**
   （直接答等于让模型凭记忆背法条，条号容易错；先召回再精排把模型的自由度限制在 10 条候选里。检索本身用字符 2/3-gram 余弦 + 标签加权，零依赖、离线可用，108 条规模下够用。）

4. **用户提到"商家太坑了"这种口语，系统怎么理解？**
   （事实提取的 prompt 里明确要求把口语转成规范书面语；类别、问题类型都有固定枚举约束；金额要求输出纯数字。）

5. **Step 3 和 Step 6 为什么能并行？并发是在哪一层做的？**
   （两者都只依赖事实和法条，用 `ThreadPoolExecutor(max_workers=2)`；注意 FastAPI 这边同步管线是通过 `run_in_threadpool` 丢进线程池的，不阻塞事件循环。）

6. **为什么要做"任务式生成 + 轮询"，不直接同步返回？**
   （LLM 全流程可能 30–50 秒，云调用/网关有超时风险；拆成"创建任务 → 轮询进度"后，请求都是短请求，前端还能拿到骨架和进度，用户不会白屏。）

7. **任务状态存在内存字典 `TASKS` 里，有什么问题？**
   （多实例部署时轮询可能打到另一台机器上就查不到；进程重启任务丢失。现在靠 1 小时 TTL 清理。要改成生产级方案就换成 Redis 或数据库持久化。）

8. **免费额度是怎么限制的？会不会被绕过？**
   （`usage_stats` 表按 user_id 累加，`_check_quota()` 在生成接口入口拦截，超限返回 403 + `code=4031` 给前端识别。管理员账号走 `admin_user_id` 白名单免限。风险点是游客 user_id 由客户端生成，清缓存就等于重置额度——要真正防刷必须绑定登录态或设备指纹。）

9. **token 过期了会怎样？能不能立即让某个 token 失效？**
   （查询 SQL 自带 `token_expires_at > datetime('now')`，过期即查不到；因为 token 是落库的，把该字段改掉就能立即失效——这正是选它而不是 JWT 的原因。代价是每次请求多一次查询。）

10. **数据隔离和并发写的边界在哪？SQLite 撑得住吗？**
    （隔离靠 SQL 里的 `user_id` 条件，没有"先查后判"的写法。SQLite 开了 WAL 模式，读并发没问题，写是串行的；现在单实例 + 低频写够用，量的量级上来要换成 MySQL/PostgreSQL——迁移主要是改 `database.py` 的连接层和占位符，业务代码基本不动。）
